# 实控人变更与要约收购·逐条挂源

把**一次控制权变动**拆成八项要素，逐项挂公告原句与锚：谁出让、谁受让、多少股、多少比例、
多少钱、变更前后控制权归谁。**比例与对价只认披露写的**——不拿股数乘价格，不拿两个数相除。

**切割句**：本件只管**控制权归属的变动过程**。分红回购减持的股东行为结果归 `cn-shareholder-return`；
并购重组的交易进度（停牌／预案／过会／实施）归 `cn-restructuring-tracker`；
质押与解押明细归 `cn-share-pledge-tracker`。本件不判利好利空，不推断新实控人后续动作。

## 0. 是什么 / 不是什么

| 是 | 不是 |
|---|---|
| 控制权归属的**变动过程**：谁取得、以什么方式、多少钱 | 分红回购减持的结果登记（那是 `cn-shareholder-return`） |
| 六类路径：协议转让／表决权委托／二级市场增持／要约收购（含部分要约）／司法拍卖／继承 | 并购重组的交易进度追踪（那是 `cn-restructuring-tracker`） |
| 八项要素逐项挂原句与锚 | 一段「公司控制权发生变更」的概述 |
| 比例与对价**只认披露原句写的** | 拿变动股数乘价格算对价、拿两个数相除算比例 |
| 要约价与溢价率**分列两行** | 把溢价率拿要约价和市价自己减出来 |
| 公告没写的写「未取到」 | 用常识、行情或推断补上 |

## 1. 触发场景

- 用户拿到权益变动报告书、详式权益变动报告书、要约收购报告书，问「谁成了新实控人、花了多少钱」。
- 用户问「这次转让了多少股、占多少比例、价格多少」。
- 用户问「要约价是多少、溢价率多少、是不是部分要约」。
- 用户要把表决权委托、司法拍卖、继承这类非交易路径的控制权变动登记清楚。

## 2. 取数纪律

1. **只认披露原文**：每项要素都要能回到一份报告书的原句与锚（`[S#]`）。新闻、股吧、研报转述一律不作来源。
2. **八项要素齐**：变更方式、出让方、受让方、变动股数、变动比例、交易对价、**变更前**控制权归属、
   **变更后**控制权归属。缺一即发；公告没写的，整项写「未取到」并进未取到清单，**不许补常识**。
   （「变更前后」拆成两格，是因为这两格常常分别是两个人名——合成一格会让「前是谁、后是谁」读不出来。）
3. **比例只认原句**：变动比例的百分比必须出现在**该行自己的书名号原句**里。公告只写股数不写比例时，
   本件判「未取到」，不替你拿变动股数去除以总股本——分母可能是总股本、可能是剔除回购专户后的股本、
   可能是表决权口径，算错一个分母，控制权读数就全错。
4. **对价只认原句**：交易对价金额必须出现在该行原句里。**不许拿变动股数乘每股价格自己算总价**——
   公告常写「转让价格以协议为准」「另行约定」，乘出来的那个数是卡面编的。
5. **要约价与溢价率分列**：要约收购（含部分要约）时，`要约价` 与 `溢价率` 各占一行。
   **溢价率披露没写就不许自己算**——溢价率的基准价（前 30 日均价／前 1 日均价／停牌前价）公告必须在场，
   拿要约价减市价再除，基准一错整条读数就错。
6. **未取到两向点名**：头部「共 N 项要素·未取到 M 项」只写一处，N 与 M 都必须等于要素明细段的实际行数与
   「未取到」行数；多报是虚报，少报是漏报，两个方向都发。
7. **不写「不适用」**：把「未取到」写成「无此项／不适用／无需披露」是替公告下结论，不是登记。
8. **判断留人工**：利好利空、新实控人后续动作、控制权稳定性、对股价的影响，全部进「待人工」。

## 4. 数据通道（以 live catalog 现值为准）

真实任务走通道正路：先看目录，再取报告书正文与附件。

```bash
# 1) 看目录，拿端点
curl -s https://cuecue.cn/api/mcp-catalog | head -c 500

# 2) 按 MCP 协议握手，确认三枚工具在场
curl -s -X POST "$MCP_ENDPOINT" -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

拿到端点后确认 `parse` / `get_parse_status` / `read_result` 三枚在场，
再用 `parse` 把报告书 URL 或本地路径交给通道，`get_parse_status` 轮询，`read_result` 取正文与表格。

**零 key 降级**：没有 `CUE_API_KEY` 时本件只走用户直供的报告书正文与本地文件，代价是取不到渠道侧的披露原文与附件正文解析，锚只能落在用户给的那份上，跨文件核对做不了。

## 5. 合规红线（随套件）

- 不判利好利空（利好、利空、重大利好、中性偏多、提振股价、压制股价）。
- 不推断新实控人后续动作（后续将注入、预计将重组、或将受让更多、意在借壳、旨在注入）。
- 不预测股价（股价将、股价会、有望上涨、看多、看空）。
- 不给评级与目标价（目标价、评级、买入评级、增持评级、强烈推荐、建议买入、建议卖出）。
- 不承诺收益（稳赚、必涨、必跌、零风险、包赚）。
- 不代拟、不代算、不代申报、不代客。
- 不裁断效力（变更是否有效、是否违规、是否合规、是否构成控制权变更）。

## 6. 快速流程（用户视角）

1. 把权益变动报告书、要约收购报告书（URL 或本地文件，可多份）交给本件。
2. 本件逐项登记八项要素，每项挂原句与锚。
3. 要约路径另登记要约价与溢价率两行（披露没写就写「未取到」）。
4. 公告没写的进未取到清单，点名要回哪份文件；判断类问题全部进「待人工」。

## 7. 机检

```bash
python3 -B scripts/check_control_change.py <变更卡.md>     # 五道码逐条发红，全过则 PASS
python3 -B scripts/check_control_change.py --selftest      # 好样须过、坏样五枚各发其码
bash scripts/fixtures/run_fixtures.sh                      # 离线样例三档（零网络零计费）
```

五道码：`CC-STRUCT` 六段齐·八项要素行级在场·申报数两向对齐／`CC-QUOTE` 原句非空·锚值非空·`[S#]` 在场且能在来源索引里找到／
`CC-CALC` 不得自算（比例与对价必须在本行原句里、溢价率不许自己减）／`CC-LINE` 红线三道／
`CC-BOUND` 写成股东回报、重组进度或质押明细时点名改走对应件。
