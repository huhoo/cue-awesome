# 民事二审翻案工程·论断逐条带出处

## 开宗：这门牌只有四个动词

**一审你委托了律师，还是输了。二审轮到你亲自指挥——本技能不承诺翻案，它把案子从律师的脑子里，交回最懂它的人手上。**

你要做的全部动作收在四个动词里，每个动词都有明确的落点文件：

| 动词 | 做什么 | 落点 |
|---|---|---|
| **盘点** | 把判决书拆成推理链，再把败诉分成三面：天然不利的、打法失误的、裁判层错误的 | `assets/判决书拆解表.md` + `assets/败诉三面表.md` |
| **搜集** | 逐字比对原始材料与判决摘录；差出来的那口气列成待调取——调取证据、责令提交、二审新证据清单三份申请 | `assets/证据比对表.md` + 待调取三份申请 |
| **查证** | 每条事实挂 A/B/C 等级，每条条号留「递交前核对」那条线；未核实的一律不进文书 | `assets/事实台账.md` + 红线清单 |
| **todo** | 把前三件排进日历，按 T+0／T+1~3／T+4~7／死线倒推 | `主控清单.md`（前提确认表 + 待办表） |

下面 Phase 0-6 不是这四个动词之外的第五件事，**它们是这四个动词的细则**。

### 第一天：今天三步

今天只做三步，每步都记着「不做会怎样」：

1. **确认送达日，算死线。** 民事判决的上诉期 15 日，自送达次日起算；两个日期一律**以判决书尾部与送达回证为准**，不凭记忆推算。不做会怎样：上诉期届满不可恢复，一审判决生效，全盘被动。
2. **查保全状态。** 已保全 →《继续保全申请书》列为最高优先级（上诉不自动延续保全）；未保全 → 先估一审判决驳回后对方转移财产的空间。不做会怎样：保全被解冻或届满释放，即便翻案也拿不到钱。
3. **查委托现状。** 律师已解除 → 上诉状删掉代理人那一行，并**书面**变更送达地址。不做会怎样：文书寄给旧代理人或旧地址，关键期限在你不知情中被消耗掉。

这三步就是 Phase 0 的头三项；第 4 项（初始化案件目录）之后才轮到拆解与比对。

## 目的

把一份**败诉判决书**加一堆**零散材料**（起诉状、庭审笔录、录音转文本、聊天截图、查询结果），工程化地转化为一套可直接递交的二审作战体系：一份上诉状、一套配套文书、一张事实台账、一份按优先级排序的待办。

本技能不提供法律意见，也不替代律师。它提供的是**结构化工作流与纪律约束**，核心解决三个问题：

1. **定位真正的败诉原因**——多数败诉不是"证据不足"，而是争点被框错、法律路径被漏审、关键事实没进入法官视野。
2. **把论证铺成阶梯而非单点**——避免押注单一请求权基础，一旦不被认可即全线失守。
3. **让每一句话都有出处**——杜绝推断与虚构，杜绝同一份材料前后矛盾。

## 何时使用

出现下列任一情形时启用：

- 一审判决败诉，需要决定是否上诉、如何上诉
- 需要拆解判决书、找出可以攻击的点
- 需要起草或复核上诉状
- 需要准备二审配套文书（继续保全、调取证据、责令提交、到庭接受询问、新证据清单）
- 当事人自行诉讼（不委托律师），需要明确期限、递交渠道、费用
- 需要在上诉期内压缩出一套可执行的作战方案

## 边界与前置声明

**开工前必须向使用人明确：**

1. 本技能产出的是**工作稿与结构**，不是法律意见；关键法条条号、期限、费用标准须由使用人核对。
2. 模型可能记错法条条号。**所有引用条号处必须标注"递交前核对条号"**，不得让使用人直接照抄。
3. 对事实的定性一律以**可核验的来源**为准；网络检索、第三方平台信息须标注为"待以官方来源核对"。
4. 涉及投诉法官、投诉律师、信访、举报的内容**另开文件**，不得混入诉讼文书与论证主线。
5. 交付文件中对身份证号、手机号、住址、银行账号、未成年人信息一律留占位符。

### 预期管理

二审改判、发回重审的比例历来不高，**本件不赌翻案**。它只把可控的部分做完：重新框争点、取回被截断的、看住钱和期限。裁判结果不由本件决定；把四个动词做完，你手里得到的是**一套有出处的表、一份能递交的上诉状、一张倒排到死线的日历**——本件的承诺到此为止。

### 防二次收割：三道警

败诉之后最容易被再收一次钱、再误一次事，三条逐个自查：

1. **解冻与转移的迹象**：一审驳回后，对方可能申请解除保全并转移财产。出现这类迹象，第一反应是《继续保全申请书》与保全届满日，不是先写上诉状——这就是硬约束 5「钱 > 期限 > 证据」的用处。
2. **「包赢」代理与来路不明的模板**：宣称包赢、包翻案的代理，以及不看你卷宗就发来的「二审改判模板」，一律按风险处理。本件要求每个论断带出处与等级（硬约束 2）；一份不基于你的在案材料生成的文书，递上去只会多一处要更正的定性（硬约束 4）。
3. **自媒体的法律答案**：短视频与帖子里的「二审就这么写」，不核对法条原文与现行有效版本就不使用。检索得到的候选一律先挂 C 级、标「待以官方来源核对」，递交入卷后方可升 B（与 `README.md` §二 检索桥同一套纪律）。

### 最小外包：单点付费，不是重回全委托

本件的默认是**你指挥**。两种情形值得再掏一次钱：标的金额大；或程序资格存疑——是否算二审新证据、能否增加诉请、当事人能否作证，这类问题硬约束 8 不许本件替你判断。

做法是**一次要点核验**，不是重新委托：带上 `事实台账.md` 与 `复核报告.md` 的『序：一句话结论』『二、扭转路径』两节，把要问的写成三个具体问题，请人只核这三点；核完仍由你更正、由你递交。外部意见同样标注为待核，不直接顶替你的事实等级（三问的具体写法与边界见 `references/05-self-represented-filing.md` §十二）。

## 八条硬约束（违反即返工）

| # | 约束 | 说明 |
|---|---|---|
| 1 | **判决自认优先** | 论证起点必须是**判决自己已认定的事实**。这类事实最难被驳，也最省力。 |
| 2 | **每个论断带出处与等级** | 三级：**A＝判决已认定**／**B＝在案已提交但未经认定**／**C＝待调取或待核实**。禁止把 C 当 A 用。 |
| 3 | **不预断、不虚构、不推断** | 未核实事项一律标注"待核实"，禁止写入文书。对款项流向、身份归属等易错事实，统一使用**开放式/择一**表述。 |
| 4 | **定性更正必须全库执行** | 一旦某事实的定性被更正（如项目名称、时间、主体归属），必须检索全部既有文件更正，并在更正处留痕说明"前一版结论作废"。 |
| 5 | **钱 > 期限 > 证据** | 财产保全与上诉期限优先于一切取证动作。顺序不可颠倒。 |
| 6 | **情绪线与诉讼主线分离** | 追责、投诉、不满另立文件。 |
| 7 | **输出脱敏** | 见边界第 5 条。 |
| 8 | **不替代程序资格判断** | 是否属于二审新证据、能否在二审增加诉请、当事人能否作证等程序问题，必须显式核查后给出结论，不得想当然。 |

## 工作流细则（Phase 0-6）

### 门牌 → 细则 → 落点（从这表进 references）

四个动词覆盖全部 Phase。**Phase 3 不在四个动词之外，它是「盘点」的后半段**——只看清败在哪不够，还得把论证重新铺一遍：

| 动词 | 细则 | 方法文档 | 落点 |
|---|---|---|---|
| **盘点** | Phase 1 拆推理链、三面归置；**Phase 3 重铺阶梯** | `references/01`（含 §三面归置）、`references/03` | `判决书拆解表.md` + `败诉三面表.md` + `法律阶梯表.md` |
| **搜集** | Phase 2 逐字比对；Phase 5 的三份申请（调取证据／责令提交／新证据清单） | `references/02`、`references/05` §八 §九 | `证据比对表.md` + 三份申请 |
| **查证** | Phase 4（**贯穿 Phase 1-3，不是最后才做**） | `references/04` | `事实台账.md` + 红线清单 |
| **todo** | Phase 0 前提确认、Phase 6 重排与递交 | `references/05` | 主控清单（前提确认表 + 待办表） |

每份 references 开头都有同一格式的**门牌锚点**（动词／Phase／落点／读到哪为止），按锚点走即可，不必回查本表。

### Phase 0 · 收口（最先做，不超过半天）

1. 确认**判决送达日**，据此计算上诉期（民事判决 15 日，自送达次日起算），得出死线日期。
2. 确认**保全状态**：是否已保全、保全金额、保全届满日、一审驳回后是否面临解冻。**若已保全，把《继续保全申请书》列为最高优先级**——上诉不自动延续保全。
3. 确认**诉讼主体与代理人现状**：是否有代理律师、是否已解除、送达地址是否为本人。**若已解除委托而文书仍列律师，必须删除该行并书面变更送达地址**，否则期限照常计算而当事人收不到通知。
4. 用 `scripts/init_case.py` 初始化案件工作目录，生成五张表、主控骨架与今日三件事.txt（枚数以脚本自报行为准）。

### Phase 1 · 判决逆向工程

目标不是"找错误"，而是**还原法官的推理链**，判断争点被框定在哪一层。

1. 逐段摘录判决的"本院认定"与"本院认为"，**还原成一条推导链**（如：A → B → C → 驳回）。
2. 找出**框架层错误**：本案的核心问题被表述成了什么？若被表述为"某人是否有代理权／某文件是否有效／某形式是否具备"，则举证责任往往已被转到弱势一方。**判据：若按该框架举证，所需证据是否全部由对方单方控制？若是，框架极可能被框错。**
3. 列出**应适用而未适用的条文**：适用条文清单 vs 本案可能涉及的请求权基础，逐条比对。
4. 填入 `assets/判决书拆解表.md`。

详见 `references/01-judgment-reverse-engineering.md`。

### Phase 2 · 证据逐字比对

1. 把判决书对每一份证据的摘录，与原始材料（录音转文本、聊天记录、书证）**逐句对照**。
2. 重点标记三类：**被截断**（摘录到某句即打省略号）、**被省略**（整段未提）、**被割裂**（同一陈述只采信其中一句）。
3. 对每一处差异，写明：原文是什么、判决写了什么、该差异影响哪个法律要件的认定。
4. 若发现判决疑似只接触到片段（如转文本节选），把"提交完整版 + 申请当庭播放原始载体"列为二审动作。
5. 填入 `assets/证据比对表.md`。

详见 `references/02-evidence-diff-protocol.md`。

### Phase 3 · 法律路径阶梯

1. 识别本案的**责任归属问题**（谁应为该行为或该笔款项负责）。
2. 列出全部可能的请求权基础，按**主攻 → 备位 → 兜底**排序，形成阶梯。
3. 逐层填写：构成要件／本案已有证据（标 A/B/C）／缺什么／怎么补／判决漏了什么。
4. **关键判据：阶梯的前几层应当不依赖任何新证据**，只建立在 A 级与 B 级证据之上；依赖新证据的层级放在后面并注明取证路径。
5. 填入 `assets/法律阶梯表.md`。

详见 `references/03-legal-ladder.md`。

### Phase 4 · 事实台账与纪律

1. 建立事实台账，每条事实标注：内容／来源／等级（A/B/C）／是否已用于文书／纪律备注。
2. 输出**纪律清单**（红线）：哪些表述禁止使用、哪些事实未保全前不得引用、哪些时间只能写区间不能精确到日。
3. 建立**更正留痕机制**：任何定性变更后，检索全库更正。

详见 `references/04-fact-ledger-and-discipline.md`。

### Phase 5 · 文书包产出

产出结构见 `references/06-document-pack.md`。要点：

- **上诉状**：理由之前加一段**总述**（一页内：一个核心争点 + 判决自认的关键事实 + 三项致命错误）。法官时间有限，总述决定他会不会往下读。
- **配套文书**：继续保全、调取证据、责令提交、到庭接受询问、新证据清单——**必须与上诉状同日递交**，否则很可能书面审理、不开庭。
- **同步机制**：上诉状每次修改后，同步更新配套文书包与主控清单中的对应段落，并在版本说明中记录。
- **导出 Word 递交稿**：成文后用 `scripts/export_docx.py` 把 markdown 转成 .docx（公文体：A4、仿宋三号、首行缩进 2 字符、页脚页码）。**只做格式投影，不重写一个字**；转完必跑 `--check` 做文本覆盖校验。详见 `references/06-document-pack.md` §Word 递交稿。

### Phase 6 · 待办与递交

1. 按 T+0／T+1~3／T+4~7／死线 重排待办，每项标注"为什么"与"产出"。
2. 核对递交渠道、份数、费用、缴费期限。
3. 输出风险清单与纪律清单。

详见 `references/05-self-represented-filing.md`。

## 交付物约定

每个案件至少产出：

1. **主控清单**（待办 + 案件档案 + 文件索引 + 纪律）
2. **复核报告**（败诉根因 + 扭转路径 + 命门证据 + 待办）
3. **上诉状**（含总述）
4. **配套文书包**（同日递交）
5. **五张表**（拆解／比对／阶梯／台账／败诉三面）——模板在 `assets/`，枚数以 `scripts/init_case.py` 自报行为准
6. **Word 递交稿**（`.docx`）：上诉状与配套文书包各一份，公文体排版、页脚页码，`--check` 校验零丢失

交付前自检：

- 每一处事实论断是否都带 A/B/C 等级？
- 每一处条号是否都标注了"递交前核对"？
- 是否存在把 C 级当 A 级使用的表述？
- 定性更正是否已在全库执行并留痕？
- 敏感信息是否已脱敏？
