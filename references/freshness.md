# 时效校验（check_freshness.py）

期刊最容易出的事故不是写错，是**写得早/写得晚**：把没发生的事写成已发生，
或者把上一期的旧闻重发一遍。`check_freshness.py` 把这两件事变成可自动判定的规则。

```bash
python3 <skill>/scripts/check_freshness.py \
    --content content.json --issue-date 2026-09-17 --window 6
python3 <skill>/scripts/check_freshness.py --content content.json --issue-date today --strict
```

`--strict` 在出现 ERROR 时退出码 1，可挂在 CI 或作为「+draft 之后必过」的门禁。

## 三条规则

| 级别 | 规则 | 判定 | 怎么处理 |
|---|---|---|---|
| ERROR | `FUTURE` | 事件日期 > 本期出版日 | **拦下**。把「拟」「预计」写成既成事实是硬伤，付印即事故 |
| WARN | `STALE` | 事件日期早于收录窗口 | 删掉，或在 `meta.freshness_exceptions` 里写明为什么它仍然是本期内容 |
| INFO | `STATED` | 正文含「将于 / 拟于 / 预计 / 计划 / 尚未 / 下一步」 | **付印当天**逐条回官网复核状态是否已变 |

日期从两处取：`unit.meta`（如 `2026.09.16 香港特别行政区政府`），
取不到再退到正文前 60 字。写法建议：**meta 里的日期必须是事件日，不能是打印日**。

## 窗口怎么定

双月刊 → 6 个月；季刊 → 3~4 个月；年刊 → 12 个月。
判断标准是「上一期出版日到这一期出版日」，不是自然上的半年。

**STALE 只查「法规动态」类条目（unit_list）**。深度文章本来就是回顾性叙述，
里面引用一年前的立法背景是正常的；早期版本对文章也查，全是误报。

## 例外的写法

```json
{
  "meta": {
    "issue_date": "2026-09-17",
    "window_months": 6,
    "freshness_exceptions": [
      {
        "match": "香港：大型股发行人气候相关披露",
        "reason": "日期标注为义务起点（自 2026 财政年度起），属本期发行人仍须履行的现时义务，非既往事件"
      }
    ]
  }
}
```

`match` 按标题前缀匹配。**每条例外都必须写 reason**——
理由是给编辑看的：没有理由的例外等于把告警勾掉，等于没校验。

## 实战里它抓到过什么

第 22 期首次跑，输出 7 条 STALE：最老的一条是 13 个月前生效的可持续披露准则
（应属上一期），还有 3 条是半年以上的补充性动态。这些条目本身写得没错，
**错在它们不属于这一期**——肉眼很容易放过，因为它们读起来都很专业。

收录区间的自检也很有用：清理前输出 `2025-08-01 → 2026-09-16`，
而栏目导语写的是「本期收录 2026 年 4 月至 9 月」——**自相矛盾**，
是一眼可见的硬伤。清理后区间收窄到 `2026-01-01 → 2026-09-16`，导语同步改到 3 月起。
